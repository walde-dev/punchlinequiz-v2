Implementation notes — Referral & Invite Rewards

Project: PUN Referral & Invite Rewards (PUN-71..75) · Started: 2026-06-01 · 3 phases · Prior notes archived: implementation-notes-contributor.html, implementation-notes-profiles.html

Settled (grilling): sources = invite link by @handle (/i/$handle) + challenge-link auto-credit; first-touch localStorage token; edge recorded at onboarding (claimHandleFn), reward on referee's first correct answer; two-sided asymmetric (+300 referrer / +150 referee, tunable); self-referral block + per-referrer daily cap; per-referral XP + profile count (milestones/streak-freeze/badges deferred); inline highlighted invite card on profile; single referrals table; payoff = in-app pull (unseen flag), push deferred to PUN-22.

Design decisions

P1Single referrals table as edge + ledger

packages/db/src/schema.ts: unique on referee_clerk_id (one referrer per user, first-touch via onConflictDoNothing). Row holds status (pending→confirmed), snapshot referrer_xp/referee_xp, seen_at (payoff), timestamps. No separate grant table needed — the status transition is the idempotency guard.

P1Confirmation hooked in grant path; cfg passed in to break the import cycle

confirmReferralOnActivation(clerkId, cfg) called from grantPrimary (artist+cloze) and grantDailyArtist (correct answers only) in lib/xp.ts. referral.ts does NOT import xp.ts — the grant caller passes the already-loaded XpConfig in, so there's no circular dependency. Wrapped in .catch(()=>{}) so a referral hiccup never breaks a grant.

P1Attribution only on first onboarding

claimHandleFn reads onboardedAt before the claim; recordPendingReferral runs only when this is the user's first onboarding (!before.onboardedAt) and a token is present — never a returning re-claim.

P1Daily cap zeroes the referrer reward, still confirms + pays referee

When the referrer is at/over referralDailyCap confirmed-and-rewarded referrals for the UTC day, the edge is still confirmed but referrer_xp=0; the referee's welcome bonus still pays (not farmable for the referrer's gain). Verified: cap 0 → referrer +0, referee +150.

P2Client carrier uses a type-only import (no server leak)

lib/referral-client.ts imports ReferralToken with import type only, so the server-only referral.ts (and its db import) never enters the client bundle. First-touch: setReferralToken refuses to overwrite an existing token. Consumed + cleared in OnboardingGate at claimHandleFn.

P2Challenge token set unconditionally on /c/$slug mount

Set on every challenge-page mount (first-touch wins), not gated on signed-out — a token is only ever *consumed* at a brand-new user's onboarding, so setting it for an existing signed-in visitor is a harmless no-op. /i/$handle uses a lightweight getInviterFn (handle → {handle, imageUrl}) for the hero, not the full profile fetch.

Deviations from spec

None yet.

P3Owner-only highlighted invite card + payoff mirrors contributor loop

InviteCard in u.$handle.tsx (rendered only when data.isOwner): bordered border-primary/40 bg-primary/5 card with the /i/$handle link (copy + native share), referral count, and confirmed list. Fetches getMyReferralsFn on mount; newly-confirmed (unseen) referrals fire a confetti '@x followed your link!' payoff then markReferralsSeenFn — same unseen-flag pattern as the contributor 'your bar is live' celebration. Reward XP shown per row; omitted when 0 (daily-cap-blocked).

Tradeoffs considered

P1Confirmation check: unconditional lookup vs a users flag

Chose an unconditional indexed lookup on referrals(referee_clerk_id) after each correct answer (no-op once confirmed / for non-referred users) over adding a users.pending_referral flag to skip the query. The grant path is a low-QPS quiz-answer path already doing several queries; one extra sub-ms indexed lookup is negligible and avoids extra denormalized state to keep in sync. Revisit with a flag only if profiling shows it matters.

Open questions

Referral confirmation push notification (PUN-22)

The referrer only sees the '@x joined! +XP' payoff on their next profile visit (in-app pull). A push (email/realtime) would close the loop faster — deferred to the Notifications project, same hook as the contributor acceptance push.

Milestones / streak freeze / referral badge deferred

v1 is per-referral XP + a profile count only. Milestone bonuses, a streak-freeze reward, and a referral badge/flair are out of scope (badges → Achievements & Badges project; streak freeze = a new consumable mechanic).

Anti-abuse is self-referral + daily cap only

No device/IP fingerprinting — a determined multi-account farmer (distinct Clerk emails, each playing one bar) can earn up to the daily cap. Defaults: referrer +300, referee +150, cap 10/day (all tunable in the admin XP screen). Confirm the values, and whether a device heuristic is wanted before launch (no live traffic to observe abuse yet).

Challenge token set for all /c/$slug visitors

First-touch, only ever consumed at a brand-new user's onboarding (harmless no-op for existing/signed-in visitors), so any anonymous visitor who later signs up credits the challenge creator. Flag if you'd rather only set it for signed-out visitors.
