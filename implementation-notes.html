Implementation notes — WHO DAT?! YouTube punchline ingestion

Spec: .context/whodat-ingest-spec.md (post-grill) · Linear cf0763ff / PUN-140..171 · Started: 2026-06-07

The spec doc records the design decisions reached during /grill-me. This file records what changed or was decided during implementation.

Design decisions

Shared core lives in apps/web/src/lib/ingest-core.ts, db injected

Both the web add-flow (upsert.ts) and the CLI import the same resolve/insert primitives. The db handle is passed in (not imported) so the CLI supplies its own createDb(DATABASE_URL) connection and the app keeps using its lazy proxy. Verified the reuse graph (deezer→admin) is tsx-safe: runtime deps are only node:crypto / @workspace/db / the inert db proxy; the auth import in admin.ts is type-only and erased by esbuild.

song.artistId = the correct quiz artist, not the song's primary credit

The reveal credits e.g. "Ansu, Tom Hengst & Cato – HELD" but the quiz answer is "Tom Hengst". The game derives the correct answer from punchlines→songs→artists, so the song row must be attributed to the correct artist. The full credit is used only to improve Genius/Deezer lookup.

Frame segmentation = long static runs + fuzzy line clustering

Validated on a real episode: a settled overlay is a static graphic held for seconds, so we sample 1fps, crop the overlay band, and keep the middle of each run ≥MIN_STATIC samples (scripts/ingest/frames.ts). Question/reveal frames of one item are merged by Levenshtein line-similarity (extract.ts) — tolerant of OCR slips like "Dass"/"Das". Defaults favour recall; all thresholds are env-tunable and measured by ingest:eval. On the sample episode: 10/10 items found, 8–9 fully auto-resolved, the rest flagged for the reviewer.

Global line dedup (idempotency)

findDuplicateLineGlobal (ingest-core.ts) matches a bar across any song by squashing both lines to [a-z0-9]. Needed because re-extraction has minor OCR/song variance, so a song-scoped check let near-dupes through. Verified: forced re-ingest now inserts 0 new rows (9 inserted → re-run 9 duplicate). Primary idempotency is still the episode ledger (poll skips done); this is the second layer for resume + cross-episode dupes.

Items with no extracted answer are recorded, not minted

If no green reveal was captured (no correct answer), we can't form a valid bar and never guess one. The item is written to ingest_items as failed with its raw extraction (so it's in the ledger + logs, not silently dropped) but no punchline is created. low_confidence therefore cleanly means "bar minted but flagged".

Deviations from spec

Captions workstream cut (PUN-146, PUN-153)

Spec assumed free German auto-subs as a cross-check. Verified: zero captions (auto or manual) on any of 5 sampled episodes. Vision-only; Genius title-search is the validation/resolution signal.

Insert active=true, not active=false (PUN-160)

Every player-facing query requires reviewed=true AND active=true; daily challenge needs an explicit admin schedule. So reviewed=false alone quarantines a bar, while active=false would hide it from the review queue (which filters active=true). Confirmed with founder.

No ffmpeg full-frame scene-detection (PUN-148/149)

The quiz is an overlay on continuous talking-heads video; full-frame scene cuts track camera/people, not overlay state. Instead: ~1fps sample → crop overlay band → perceptual-hash dedup → Gemini groups by the on-screen "X/10" counter, merging each question-card frame with its green reveal frame.

Tradeoffs considered

Single Gemini provider vs 3-way bake-off (PUN-151)

Committed to Gemini 2.5 Flash (spec default, cheapest capable vision) + a reusable eval harness, rather than building a 3-provider bake-off. Validated empirically: a real question-card and reveal frame both extracted perfectly (line w/ umlauts, 3 options, green correct index, song credit, X/10). Alternates only revisited if it misses the gate. Cost ≈ $0.01/episode (~125 frames).

neon-http has no interactive transactions → app-level dry-run

The DB driver (@neondatabase/serverless neon-http) can't do interactive transactions, so per-item work isn't wrapped in one. --dry-run (the default) does all read-only resolution + dedup but writes nothing, rather than insert-then-rollback. On a hard failure mid-item, auto-created artists/songs may be left without a bar — harmless and reusable; the global line dedup keeps a re-run from duplicating.

Open questions

Golden set needs real hand-labeling (PUN-170)

scripts/ingest/golden/NI7V8j3CCZM.json is a seed: 8 of ~10 items, machine-extracted then spot-verified, not fully independently labeled. The gate currently reads correct 100% / line 100% / options 87.5% (one distractor OCR variant) → "FAIL" only on the options threshold. Please hand-label 3 full episodes (watch + transcribe) before trusting the gate at volume — see golden/README.md.

~1–2 items/episode have no captured reveal → flagged, not auto-answered

When the green reveal frame isn't sampled, the item is recorded as failed (no answer) and not minted. Lowering INGEST_MIN_STATIC raises recall at the cost of more frames. Want me to tune for higher reveal recall, or is "flag the few for the human" acceptable?

Distractor artist near-duplicates aren't fuzzy-merged (PUN-156)

resolveOrCreateArtist matches existing artists by exact name/slug only. An OCR variant of a distractor name (e.g. "Wa2zermann" vs "Wa22ermann") can create a near-duplicate artist row. The admin can merge these; full fuzzy artist-dedup was left out of v1 scope. Worth adding?

drizzle-kit migrate didn't apply DDL over neon-http

FYI/ops: pnpm db:migrate reported success but didn't create the tables (neon-http needs a websocket driver for migrations); I applied 0023's SQL directly. When you run migrations for real, use a direct/websocket DATABASE_URL or apply the SQL directly. Migration 0023_complete_the_twelve.sql is committed and correct.
