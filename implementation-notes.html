Implementation notes

Spec: Profiles project — Phase 1 (migration + PUN-5) + Phase 2 (PUN-6 profile, PUN-13 boards, PUN-12 verify) · Source of truth: grilled decision ledger + enriched Linear tickets · Started: 2026-05-31

Design decisions

follows schema: composite PK + single followee index

Added follows at packages/db/src/schema.ts with PK (follower_clerk_id, followee_clerk_id), an index on followee_clerk_id, a self-follow CHECK, and cascade FKs to users.clerkId. The composite PK already indexes follower-prefix lookups (a user's following list / friends set), so the standalone follower index PUN-5 mentions is redundant and was omitted.

Auth + idempotency pattern for server fns

follow/unfollow resolve the caller via getActor(getRequest()) (same pattern as lib/leaderboard.ts), throw if the actor isn't a Clerk user, call ensureUser(callerClerkId) first (FK safety, per lib/xp.ts:105), then insert…onConflictDoNothing / delete. Both are no-ops on repeat → idempotent.

Handle-based follow on the public profile

The client only knows handles (URLs are /u/handle), and the leaderboard already exposes handle-only — so other users' Clerk ids stay server-side. Extracted doFollow/doUnfollow in lib/follow.ts; added followByHandleFn/unfollowByHandleFn in lib/profile.ts that resolve handle → clerkId then call them. The clerk-id followFn/unfollowFn (PUN-5 contract) remain.

topArtists + follow counts live in the profile loader, not the snapshot

Computed in getPublicProfileFn (lib/profile.ts), NOT folded into getProfileSnapshot — the header chip (getHeaderXpFn) reuses the snapshot on every page, and adding artist/follow joins there would tax that hot path. Top artists = bars-solved per artist, top 3.

/profile unification via redirect

routes/profile.tsx loader calls getMyHandleFn; onboarded users throw redirect() to /u/$handle. Anonymous + signed-in-without-handle users fall through to the existing self view / sign-in pitch (handle claiming is the parallel onboarding work). Single rich profile surface at /u/$handle.

follow_user / unfollow_user logged client-side (resolves the Phase-1 open question)

Emitted via logEvent in u.$handle.tsx Actions.toggle, at the button call site — matching the existing convention (server fns stay pure). Server functions were left pure as planned.

Friends/per-artist board internals (PUN-13)

In lib/leaderboard.ts: Friends uses a LEFT JOIN over the weekly XP union so everyone you follow shows even at 0 XP this week, scoped via clerk_id IN (followedSet) (self + followees). Per-artist mirrors the completion query with a songs.artist_id join filter; totalActiveLines = active lines for that artist (drives the % subLabel). For both, the "me" row is derived from the visible top list (meFromTop) rather than a second ranking query — these boards are bounded (friends set small; per-artist solvers ≤ TOP_N=100). Trade-off: a user outside the artist top-100 shows no me-row (acceptable v1).

PUN-12 verified, not rebuilt

Global all-time XP + weekly XP boards already existed and are kept on the calendar-week window (per the grilled override). Confirmed correct via the production build + a live-data query smoke test. No code change beyond sharing the row component with the new boards.

Deviations from spec

Phase-1 migration adds only follows, not all four tables

The project plan said "one migration: follows, challenges, challenge_attempts, punchline_submissions." Phase 1 adds only follows. Rationale: design the challenge/submission tables alongside the code that consumes them (Phases 3–4) so columns aren't guessed early; Drizzle migrations are cheap to add per phase. Keeps each phase's migration reviewable.

Challenge button stubbed (disabled) on the profile

PUN-6 lists a Challenge button (visitor) + Create-challenge (owner). Challenge creation is Phase 3 (PUN-8), so ChallengeButton in u.$handle.tsx renders disabled with a "Soon" tag. Will be wired when PUN-8 lands.

Review fixes (2026-05-31 manual review)

(1) Profile link added to the Clerk account menu via UserButton.MenuItems → UserButton.Link href="/profile" (which redirects to /u/$handle), keeping default manageAccount/signOut. (2) LangToggle hover aligned to the Leaderboard nav link (text-foreground/70 hover:text-primary, no ghost bg). (3) Artist-picker chevron fixed: native <select> set to appearance-none + a custom chevron SVG. (4) Profile hero reworked — see below.

Avatar persistence for public profiles

The server can't read another user's Clerk image, so the public profile couldn't show avatars for anyone but the viewer. Added users.image_url (migration 0012) + syncProfileImageFn (lib/profile.ts), called fire-and-forget from AuthSlot in app-header.tsx using useUser().imageUrl (no-ops when unchanged). getPublicProfileFn now returns imageUrl; the hero renders it with an initial fallback. Avoids Clerk backend calls + onboarding coupling.

Profile hero: avatar + @handle is the focus, XP demoted

Per review feedback. u.$handle.tsx now leads with the avatar + large @handle; the rank badge + level name are a small supporting pill; the big XP number is gone — XP moved to a thin line under the progress bar.

Phase 3 — Challenges: no XP, end-of-run server validation

Challenges grant no XP (competitive mode, not the grind — and avoids an XP farm). The 5 answers are validated server-side in one call at the end (submitChallengeAttemptFn): the correct answer is never sent to the client (no cheat vector) and per-bar correctness is revealed only in the post-submit recap. No per-bar reveal during play — keeps the timed run fast. solve_ms is client-supplied per bar, clamped server-side to [0, 120000].

First-attempt-lock + anonymous claim

challenge_attempts has UNIQUE(challenge_id, clerk_id); submit uses onConflictDoNothing so the first run is permanent (replays never overwrite). Anonymous runs are scored but not persisted; the client holds answers in localStorage (pq.challenge.<slug>) and re-submits after Clerk modal sign-in (a useAuth effect claims on sign-in, covering both modal + redirect).

Challenge creation, slug, share card, button wiring

createChallengeFn picks 5 random distinct active bars (excl. daily), 8-char base62 slug via crypto (retry on unique collision). Share card = new client-canvas renderChallengeCard (no server OG). Challenge buttons un-stubbed: profile (visitor + owner) and the session-complete screen create a challenge → navigate to /c/$slug; logged-out users hit a sign-in modal first (creation is auth-required). Board highlights the viewer via a server-returned viewerHandle.

Phase 4 — UGC submissions

punchline_submissions staging table (migration 0014): only line required; optionals are free-text (artist_hint, song_hint, answer→perfect_solution, cloze_prompt, note). /submit (routes/submit.tsx) is auth-gated (anon pitch otherwise). Admin reviews at /admin/submissions; approve reuses upsertBar (names → resolve/create artist+song+distractors + Deezer artwork), then flips the minted row to reviewed=true (+ optional cloze) and stamps created_punchline_id. Reject sets status. "My submissions" is an owner-only client-fetched section on /u/$handle (links approved bars into /play?artist=).

Open questions

Admin approve takes distractors by name (can create junk artists on typo)

The mint form passes artist/song/2 distractors as names to upsertBar (the proven add-bar path), so a typo'd distractor auto-creates a new artist. Admin-only + trusted, acceptable for v1. Could switch distractors to an ArtistSelect (existing-IDs only) if junk artists show up. Flag if you want that now.

Challenge play shows no per-bar feedback — confirm

Unlike the casual game (which reveals right/wrong after each bar), the challenge run advances silently and reveals all 5 outcomes only in the post-run recap. This was deliberate (speed + anti-cheat for the timed board). Flag if you'd rather show per-bar feedback.

Solve-time trusts the client (clamped)

The tiebreak solve_ms is measured client-side and clamped to [0, 120s] per bar server-side. A determined cheat could under-report time. Anti-cheat hardening is explicitly deferred in this project — flag if you want a server-side timer floor sooner.

Show the real Clerk name on the public profile?

The review said "make pfp+name the focus." I led with @handle as the identity (consistent with the leaderboards/URLs) and did not render the Clerk full name (e.g. "Waldemar Panin"), since the page is public and the real name is PII a user may not want exposed. If you want the display name shown (e.g. small, under the handle), say so and I'll add it (would also need persisting the name like the avatar).
