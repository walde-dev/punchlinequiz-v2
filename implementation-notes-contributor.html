Implementation notes — Contributor Rewards

Project: PUN Contributor Rewards (PUN-65..70) · Started: 2026-06-01 · 4 phases · Prior project's notes archived in implementation-notes-profiles.html

Settled design (grilling): contributor_grants ledger; flat 500 XP (tunable); attribution on play+reveal (not share card); auto-publish DEFERRED; 3 tiers (5/25, 60%/80%); tier-scaled pending-slot cap anti-abuse; contributor leaderboard accepted-count all-time; profile stats + tier chip (badges deferred); in-app pull acceptance feedback (push deferred); weekly submission streak; contributor XP → totalXp/rank/all-time only (not weekly board).

Design decisions

P1contributor_grants ledger table

New table, unique on submission_id → idempotent (one grant per accepted submission). Adds to users.total_xp via SQL math. Deliberately NOT reusing user_punchline_xp (its unique (clerk_id, punchline_id) would collide if a contributor later solves their own minted bar).

P1Flat 500 XP, tunable

New xp_config.xp_submission_accepted column, default 500. Surfaced in the admin XP tuner (routes/admin/xp.tsx + api/admin/xp-config.ts whitelist).

P1Tier computed on-read, constants in lib/contributor.ts

3 tiers (Neuling → Vertraut ≥5/≥60% → Verifiziert ≥25/≥80%; min 5 resolved before rate gate). No stored tier column — computed from submission counts. Tier-up moments detected by comparing before/after at acceptance.

Deviations from spec

P1/P3Auto-publish deferred (PUN-66 re-scoped)

Project's headline "top tier auto-publishes" is not buildable: submissions carry only line + free-text hints, but minting a playable bar needs song_id + two distractor artist FKs (NOT NULL) supplied only by the admin today. Auto-publish needs a structured submission form → later phase. Audit-sampling / takedown / revocation were guardrails for auto-published bars → defer with it. PUN-66 now = tier compute + review-queue prioritization + anti-abuse.

P4Acceptance push notification deferred to PUN-22

Notification dispatch core (Resend) doesn't exist (PUN-22 Backlog, separate project). Acceptance payoff is in-app pull (unseen-acceptance flag → celebration on next visit). Push is a clean hook for when PUN-22 lands.

P3Milestone badges deferred to Achievements & Badges

That project is unscoped/empty; building milestone badges here = the parallel system PUN-68 warns against. Tier prestige chip (surfacing computed state) ships; 10/50/100 badges hand off.

P2Contributor XP excluded from weekly XP board

Per decision: contributor grants feed total_xp (rank + all-time board) but NOT the weekly board (which stays pure play-activity). No change to the weekly UNION queries in lib/leaderboard.ts.

P2Attribution rendered via shared BarCredit in the bar header

New components/bar-credit.tsx links to /u/$handle. Threaded as submittedByHandle through Round (game.ts), DailyChallenge (daily.ts), ChallengeRound + ChallengeRecapBar (challenge.ts) via a leftJoin(users) on punchlines.submitted_by_clerk_id. Placed beside the question prompt in each route's BarDisplay so it shows during play AND through reveal (same component persists).

P2Challenge recap row omits per-bar credit

The decision was "reveal/result + during play". Attribution shows during each challenge round, but the post-run recap row (c.$slug.tsx) is a dense, truncated one-line list (✓/✗ + line + artist) — adding @handle per row clutters it. Credit is already seen while playing each bar, so the recap stays clean. Play + daily show it on reveal as specced (the bar stays on screen).

P3Submission streak built in Phase 3, reused in Phase 4

getSubmissionStreak (contributor.ts) — consecutive Mon-anchored UTC weeks with ≥1 submission, alive only if the latest active week is this/last week. Built now because PUN-68's profile stat needs it; Phase 4 reuses it for the nudge. Verified: [0,1,2]→3, [1,2]→2 (alive via last wk), [2,3]→0 (dead), [0,2]→1.

P3Review-queue tier priority sorted in JS, not SQL

Tier is computed (no column), so api/admin/submissions.ts fetches pending rows, resolves tiers via getTiersFor, then sorts: tier DESC, then createdAt ASC (oldest-first within a tier so nothing rots). Admin-only + capped at 100 rows, so JS sorting is fine and avoids a correlated count subquery in ORDER BY. Tier badge surfaced on the admin card.

P3Profile contributor section only shows when submitted > 0

Non-contributors don't see an empty contributor block. Tier chip + accepted/submitted/rate/streak tiles render via getContributorProfile on /u/$handle.

P4Acceptance celebration = pull on My submissions, marked-seen once

New nullable punchline_submissions.acceptance_seen_at. getMySubmissionsFn returns newlyAccepted (approved && unseen) + xpAwarded (joined from contributor_grants). On load, u.$handle.tsx shows a confetti celebration for fresh acceptances, logs acceptance_seen, then calls markAcceptanceSeenFn (idempotent UPDATE … WHERE seen IS NULL) so it fires once. Deep-links to play the live bar via its artist slug.

P4Progress-to-next-tier + funnel logging

nextTierProgress (contributor.ts) drives a "noch N bis Vertraut/Verifiziert" line on the profile (uses the accepted-count gap — the legible number). Funnel events: submission_created (submit.tsx, alongside legacy submit_bar), submission_rate_limited, acceptance_seen, view_contributor_leaderboard; acceptance + XP grant are logged server-side via the admin review_submission audit (xpGranted/tierUp).

Tradeoffs considered

P1Anti-abuse: pending-slot cap vs daily quota

Chose tier-scaled cap on outstanding PENDING submissions (Neuling 5 / Vertraut 15 / Verifiziert ~uncapped), rate <30% over ≥10 resolved → 1 slot, +30s cooldown. Self-regulating: accept/reject frees slots, so productive contributors flow while spammers jam their own queue. Rejected a flat daily quota (a spammer can still dump a day's junk).

Open questions

Auto-publish + structured submission form (next phase)

Deferred from this project. To let the top tier truly bypass review, the submission form must capture mint-ready artist/song/2-distractors, and we then need the audit-sampling / instant-takedown / trust-revocation guardrails. Wants its own scoping/grilling pass. The tier system + grant path are already in place to hang it off.

Acceptance push notification (PUN-22)

In-app pull ships now; the email/realtime push ("dein Bar ist live!") is a clean hook for when the Notifications project lands. Wire it into the admin approve path next to the existing in-app flag.

Contributor milestone badges (Achievements & Badges)

10/50/100-accepted + "Verified Contributor" badges intentionally NOT built here. Hand off to that project so there's one badge system. The tier chip + stats are live to build on.

Tier thresholds are code constants, not DB-tunable

5/25 + 60%/80% live in contributor.ts. If you want to retune them live like XP, they'd move into a config table. Flagged during grilling; left as constants for now. Confirm that's acceptable.
