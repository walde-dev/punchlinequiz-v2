Implementation notes — PUN-118 (signup conversion)

Spec: Linear PUN-118 (rank+handle reframe · escalating 2nd-session gate · handle-carry) · Started: 2026-06-06

Design decisions

Weekly rank computed from a raw XP value

Added weeklyRankForXp(xp) in apps/web/src/lib/leaderboard.ts (exported alongside currentWeekStartUtc), reusing the existing weekly XP union (user_punchline_xp + user_daily_xp, onboarded users only). getAnonStandingFn in apps/web/src/lib/anon-xp.ts wraps it: returns {total, claimed, weeklyRank} for the current anon session. Rank is the anon player's banked total compared against the live weekly distribution — an honest "where you'd land".

Gate triggers on session-START, in play.tsx, covering all entry points

Counter pq.sessions_completed (localStorage, lib/session-progress.ts) is incremented in session-summary.tsx when a run completes. PlayInner calls maybeOpenGate() on mount (covers logo→remount + deep links) and at the end of onRestartSession (covers in-place "Play again"). This sidesteps the buried-button problem (replay finding) without threading the gate through the round state machine.

Handle-carry via localStorage

pq.desired_handle (lib/session-progress.ts). The gate/CTA lets the user type a handle pre-auth (live availability via checkHandleFn, which already works for anon callers), saves it, then opens Clerk sign-in. onboarding-gate.tsx prefills its handle field from it and clears it on successful claim.

Gate self-guards on auth; play.tsx stays auth-agnostic

SessionGate wraps its body in Clerk <Show when="signed-out">, so play.tsx can open it purely off the counter and signed-in users never see it.

Deviations from spec

None yet.

Tradeoffs considered

Counter increment location

Considered incrementing where phase becomes "session-complete" in play.tsx vs. in session-summary.tsx's existing session_completed effect. Picked session-summary: it is the single place a finished run is observed (natural end, restart-fail end, daily), so the counter stays consistent with the event.
